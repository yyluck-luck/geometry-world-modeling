# Round 14-D — Second-consumer feasibility survey (2026-09-19)

## Scope and audit rule

This is a feasibility survey of released code, not a novelty, funding, or acceptance review. I did not download model weights, run generation, use a GPU, or modify an existing project file. I treated the five conditions in the brief as fixed:

1. an instance attribute is written on one branch or call path;
2. it is read on a different path whose own write is conditionally guarded and may not fire;
3. the documented reset/initialize/new-session path does not clear it;
4. the mixed sequence is reachable from a documented public API or shipped demo;
5. the behavioural difference is measured on frozen weights.

Conditions 1–4 are static. Condition 5 is reported separately and is **UNMEASURED/UNVERIFIED** for every system in this file because this run used no GPU. A **HIT** means conditions 1–4 all hold. **NEAR** means that at least one condition is missing or cannot be established. **CLEAN** means the inspected state is reset or re-created on the documented public path. **OUT-OF-PREDICATE** means the generation path is stateless across public calls, or the project is outside the video/world-model scope; it is not silently counted as a CLEAN stateful audit.

For every code statement below, the repository URL, inspected commit, path, and line numbers are given. A repository being public does not imply that its checkpoint, license, or released demo is self-contained.

## Q3. Honest no-GPU count

A realistic two-week target is **9 model families (about 13 released variants if Matrix-Game 1/2/3, LongLive v1/2, and Cosmos Predict2/Predict2.5 are counted separately)** for conditions 1–4: VMem, GEN3C, the Matrix-Game family, the Cosmos-Predict2 family, Self-Forcing, LongLive, FramePack, MagicWorld, and MemFlow. The present survey reached that order of magnitude by reading the public entry point, instance construction, cache/history writes and reads, reset/new-session path, and one shipped API/demo per repository.

The limiting factor is not line counting. It is the time needed to establish that the mixed sequence is actually reachable from the documented API, to distinguish UI/function state from instance state, to follow branch and version drift, and to check licenses/checkpoint availability separately. A second reviewer is also needed for borderline cases such as MagicWorld. A much larger list would mostly become NOT-INSPECTED or speculative rather than a stronger result.

## Q5. Feasibility verdict

**Zero GPU is sufficient to close the breadth gap for conditions 1–4 as a static audit.** This survey found two strict in-scope HITs (VMem and GEN3C), one strict NEAR (MagicWorld), and several genuine CLEAN systems. It also found that WorldMem and Cosmos-Predict2 do not meet the required instance-state target, rather than pretending that every released system is a positive case.

**Zero GPU is not sufficient for a credible claim about behavioural impact.** Condition 5 is the part that turns a static stale-state path into a measured defect, and reviewers are likely to treat a static-only cross-system table as code-risk evidence rather than demonstrated external validity if the paper claims output degradation or user-visible harm. A defensible contribution can therefore use the static survey to establish breadth and select the two HIT systems, but it still needs condition 5 on at least one HIT (preferably both) before claiming a cross-system behavioural result.

This conclusion is about execution feasibility under the fixed predicate. It does not rank the research directions and does not authorize a GPU run.
