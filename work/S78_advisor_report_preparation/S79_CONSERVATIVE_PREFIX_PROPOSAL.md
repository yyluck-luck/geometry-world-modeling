## 1. 两种端点，四种组合，怎样取共同前缀

令本地解码帧从0开始编号，视频共有N帧；映射值是整数c。假定官方编号基数b只可能为0或1，且c的含义只可能是“第一张不允许看的帧”或“最后一张允许看的帧”。使用半开区间 `[0,E)` 表示保留0至E−1号帧。

| 可能约定 | 换算为本地0基的允许前缀 |
|---|---|
| 0基，c为第一排除帧 | `[0,c)` |
| 0基，c为最后保留帧 | `[0,c+1)` |
| 1基，c为第一排除帧 | `[0,c-1)` |
| 1基，c为最后保留帧 | `[0,c)` |

因此：

- **若已确认映射采用0基，只剩含/不含歧义：共同前缀是 `[0,c)`。**
- **若只确认编号可能是0或1基：四种约定的共同前缀是 `[0,c-1)`。** 例如c=100时，保留本地0至98号帧，最后一张是98，不是99。
- 实际区间还须与 `[0,N)` 相交。工程表达可以写E=`max(0,min(N,c-1))`，但这只是数学截断；**不能用它把缺失、越界或特殊值“修好”后放行**。本探索先要求整数c满足 `2 <= c < N`，否则该样例不进入实验。

推导是求四个集合的交集，属于普通数学控制，不是新记忆方法。已对N=2至100、c=1至N共5,049个组合验证交集表达；零基两约定也一并检查。这个有限整数复核只确认实现没有写错该推导，不证明官方约定属于假设集合，更不证明真实视频前缀合格。[本地算术与映射回执](s79_conservative_prefix/MAPPING_AND_ARITHMETIC_RECEIPT.json)

## 2. 仍必须核实的假设

1. **映射指的是这一份原视频的帧编号。** 必须连接官方split、规范video_id、映射文件身份和实际视频；有预先重剪、抽帧、重复帧或其他时间偏移时，少看一帧没有保护作用。
2. **语义集合确实足够。** 本建议显式假定仅有0/1基和首排除/末保留四种情况；如果c可能是秒数、重采样帧号、另一个片段的局部索引或其他特殊编码，则没有由该公式保证的非空前缀。未知任意编号偏移时，不能凭经验多减几帧。
3. **值为有效的内部截断点。** 对非整数、缺键、非视频键、c≤1或c≥N保留拒绝原因。这里主动少纳入一些样例，以保持这个新探索的规则简单；不是宣称它们在官方数据中一定无效。
4. **时间在数组外也一致。** 总帧数与视频版本必须可核；若同时使用时间戳，应核其起点和与帧ID的对应。不能只凭fps相乘替代身份/编号核查。状态实验可先按帧序列推进，避免未经核实的秒级预测主张。
5. **真正消费者只收到共同前缀。** 预处理生成独立前缀产物，后续选择器/跟踪器只接收该产物；未来图像、答案、对象状态和动作标签不传入预测路径。若视频解码器需缓冲压缩流，报告实际媒体读取范围，不能把“未输出未来RGB”冒充“从未读取含未来信息的压缩字节”。

最后一点也意味着：新协议的预测时刻更早了，可能把真正有用的状态见证一并裁掉。后续若合法前缀已不含可辨信息，应记录样例不合格；不能恢复被裁掉的帧以保住假设，不能把信息不足称作模型遗忘。若未来另行修改前缀规则，应立新版本并说明看过哪些结果。
