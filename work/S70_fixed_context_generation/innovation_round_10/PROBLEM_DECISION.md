## Candidate 1: FloWM — appropriate controlled dynamics, conditional CPU feasibility

**Task and publication.** ICML 2026 is confirmed by the [official title listing](https://icml.cc/Downloads/2026). The inspected author manuscript is v2. Its 3D dataset is simulated Miniworld: colored blocks move and bounce from walls; the agent takes discrete self-motion actions. Prediction uses observed RGB plus history and **future agent actions**, not future object trajectories. Main evaluation uses 70 context frames and 70/210 future frames. This removes unspecified future camera control, not all uncertainty about unseen state. It is not real photography. [§4.3 and §6](https://arxiv.org/html/2601.01075v2).

**Exact consumer.** Code commit `c909c54a3d58ae240de03f5ebbec222d3e6b1264`, `flowm_models_3d.py:526–675`, takes `input_seq, input_actions, target_actions`; optional target RGB defaults to absent and teacher forcing to zero. The evaluation call in `algorithms/flowm_video.py:254–257` omits target RGB. Output length is the discrete target-action sequence length. `datasets/video/blockworld.py:42–53` calls ordinal frame indices “timestamps”; `load_cond:182–199` reads action IDs. The base configuration explicitly aligns actions as `t−1→t`. No arbitrary seconds-valued query-time channel was found in this path. Source comments listing three action IDs differ from the four-action dataset description; retain actual dataset/config mapping when implementing a loader. [Bound consumer](https://github.com/hlillemark/flowm/blob/c909c54a3d58ae240de03f5ebbec222d3e6b1264/algorithms/mem_wm/backbones/flowm/flowm_models_3d.py#L526).

**Availability and licence.** The code's [LICENSE](https://github.com/hlillemark/flowm/blob/c909c54a3d58ae240de03f5ebbec222d3e6b1264/LICENSE) is MIT. **CPU boundary.** The directly inspected 3D core uses PyTorch convolutions, MultiheadAttention, `roll`, `rot90` and tensor operations; no compulsory CUDA kernel appeared in that core or its two direct helper files. It directly encodes/decodes RGB, and the configured FloWM path disables latent diffusion: the separate VAE checkpoint is not a scientific core input. However, the official installer requests CUDA PyTorch, nvcc and FlashAttention, and requirements include DeepSpeed/decord/metric packages. The generic factory eagerly imports CogVideo/RSSM stacks; only the inspected SSM import is guarded. The Lightning validation entry uses `accelerator="auto"`, which is not an explicit CPU guarantee on a Mac. Therefore a narrow CPU loader preserving original model/weights, action alignment, normalization and recurrence needs separate qualification; blindly running the installation script is not the next step. No complete import-closure or macOS package-availability claim is made. [Installer](https://github.com/hlillemark/flowm/blob/c909c54a3d58ae240de03f5ebbec222d3e6b1264/setup_flowm_env.sh); [factory](https://github.com/hlillemark/flowm/blob/c909c54a3d58ae240de03f5ebbec222d3e6b1264/algorithms/mem_wm/backbones/__init__.py); [validation entry](https://github.com/hlillemark/flowm/blob/c909c54a3d58ae240de03f5ebbec222d3e6b1264/experiments/base_exp.py#L317).

**Resource bounds, not a timing promise.** With the released configuration, the 12 encoder/decoder feedforward blocks alone contain at least `12×(256×1024+1024×256)=6,291,456` matrix weights: **25,165,824 bytes in FP32**, excluding biases and all other parameters. The recurrent map is another nominal **5,575,680 bytes** (`5×33×33×256×4`) per item; intermediate maps, attention, RGB buffers and framework memory are additional. Checkpoint file size is not parameter storage or RSS. Paper Table 12 rounds model size to 10M, while Table 14 reports 12.8M; neither is our measured parameter count. Its inference timings are **H200, batch 8**, not this CPU. The released inference configuration uses batch 128/FP32 with video and neural metrics, so it should not be copied as a minimal single-case workload. No seconds or peak-RSS estimate is invented. [Configuration](https://github.com/hlillemark/flowm/blob/c909c54a3d58ae240de03f5ebbec222d3e6b1264/configurations/shortcode/exp/blockworld/flowm/infer/base_inference.yaml); [Appendix I/Table 14](https://arxiv.org/html/2601.01075v2).

The even smaller released 2D checkpoint is listed at 904,582 bytes, but its two HEAD attempts failed with TLS EOF. Its 25×64×50×50 FP32 state is 16,000,000 bytes despite the small parameter count. This reinforces why checkpoint size alone is insufficient; MNIST World would be a toy 2D scope change, not a 3D substitute.

## Candidate 2: WorldMem — released, but a less useful first CPU port

Its paper uses Minecraft actions/poses and timestamp embeddings; it also evaluates static real-scene revisits on RealEstate10K. ## Smallest worthwhile next decision

First qualify a **single-item FloWM CPU inference path**, preserving the published checkpoint/config semantics and avoiding optional video/learned-metric logging; measure actual loading, one-step memory and time before committing to a full rollout. This is ordinary engineering, outside this source-only batch. A successful one-step check proves execution feasibility only.

If qualified, the narrow failure study is one preselected Dynamic Blockworld validation episode, **70 observed frames → 70 predictions with the recorded future self-motion actions**, containing an out-of-view interval followed by reappearance. The official loader expects paired `*_rgb.mp4` and `*_actions.pt`; their metadata catalog is public, but no episode or pixels were acquired/qualified here. Dataset-card “download_size” refers to metadata tables, not the full videos/shards. Freeze episode/query/horizon before viewing outcomes; if the fixed episode lacks the required event, report ineligibility rather than hunt for a dramatic failure. Keep future RGB/state for evaluation only.

The scientific question is whether any residual reappearance error survives this already structured dynamic baseline. An error alone cannot separate unobserved state from failed memory use; the history must first contain checkable motion information, and deterministic wall-bounce rules/known actions provide an ordinary alternative explanation to test. If FloWM already preserves the relevant state, stop that proposed memory-defect direction. If it fails only after an unseen state/interaction, do not call it compression loss. If the core cannot load unchanged, required paired data is unavailable, or measured CPU cost exceeds a declared bound, stop before another long generation. Current evidence qualifies **one source-feasible simulation candidate, zero execution-verified dynamic baselines, and zero real-photo dynamic predictors**. No novelty or benefit is established.
