# S97 修正：按项目冻结规则复核 RGB-D 与 GT

## 为什么需要第二次复核

原 `RESULTS.json` 是一个**最近邻诊断**：每个 RGB 独立寻找最近的 depth 和 GT。它可以发现文件是否可读，但它会重复使用同一 depth，也可能把 RGB 错配到 GT 的长时间断点两侧。因此原结果不能作为正式的时间配对资格证明。

本次 `run_official_association.py` 保留原始诊断，不覆盖它；改用项目 `src/tum_rgbd.py` 中已经冻结的一对一关联：候选按 `(|Δt|, RGB 时间, depth 时间)` 排序，严格要求 `|Δt| < 0.020 s`，每个 RGB 和 depth 只能使用一次。GT 时间戳按项目 S8 规则划分：相邻 GT 间隔大于 `0.100 s` 就建立新的闭合支持区间；RGB 与 depth 必须落在同一支持区间内。

关联实现的源码身份固定为 `src/tum_rgbd.py`，SHA-256 为 `e6018d81e7958fad5e3fb75f59866f291067336a0cdf0cfb2f1b9197f1b3fff4`；机器可读结果也保存了该身份。

## 实际结果（2026-09-12，开发数据）

| 数据 | RGB / depth / GT 行数 | 一对一 RGB-D | 同一 GT 支持区间 | 被 GT 支持规则排除 | 图像读取错误 |
|---|---:|---:|---:|---:|---:|
| `fr1_xyz` | 798 / 798 / 3000 | 792 | 788 | 4 | 0 |
| `fr2_desk_timestamp_guard` | 2965 / 2964 / 20926 | 2893 | 2212 | 681 | 0 |

保留下来的图像全部为 640×480；RGB 为 `RGB`，深度为 16-bit `I;16`。深度非零比例的中位数为 `0.75749`（fr1）和 `0.79161`（fr2）。这些统计只说明当前本地开发数据的文件和协议配对可运行，不说明深度是无噪声真值，也不构成未见场景验证。

## 结论边界

1. 原 S97 的 `matched_gt_over_slop` 数字不能被引用为正式 GT 配对通过数；它只保留为“最近邻诊断”。
2. 官方规则显示 fr2 有 681 条 RGB-D 一对一匹配不能落在同一个连续 GT 支持区间内，因此不能直接拿全部 2965 帧做带 GT 的连续评测。
3. 两个序列均已用于项目早期开发，状态是 `DEVELOPMENT_SEEN`；它们只能用于工程调试和协议验证，不能作为 GRC-Memory 的 held-out 或跨场景确认。
4. 本轮没有模型推理，没有运行 S91，也没有验证 GRC-Memory、未来预测信息收益或任何新颖性主张。

完整机器可读证据见 `run_02_official_association_results.json`；原始最近邻结果 `RESULTS.json` 保持不变以便审计。
