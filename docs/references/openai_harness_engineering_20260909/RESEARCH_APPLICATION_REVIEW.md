# Harness 工程对本项目的有限应用建议

已独立阅读 Ryan Lopopolo 于 2026-02-11 发布的[OpenAI 原文](https://openai.com/zh-Hant/index/harness-engineering/)。核心可借鉴的是：把隐含知识变成可发现的本地证据，用小入口和可执行反馈减少反复找资料、解释状态和修补工具的时间。文章报告的是特定软件团队的工程经验，其产量、速度估计和自动合并做法不能证明本项目的科研效率或算法创新。

1. **保持短入口，整理其指向。** 本项目 AGENTS.md 实际只有 15 行，已经符合“地图”的方向，不必为了采用文章而重写。让入口指向原则、唯一当前阶段、追加式账本和该阶段的协议/源码/结果/限制；历史证据留在原处，按需查阅。
2. **下一次只修检查器的一个结构问题。** 当前检查器实际 1,400 行，仍逐段追加 S40 至 S75 的状态与叙述。建议让一份权威当前阶段描述驱动现状检查；旧阶段作为可追溯历史引用。不要继续复制“下一步”“正在检索”等文字到多个可执行分支，也不要为整理状态再造一层大型框架。
3. **机器检查事实，人判断研究价值。** 复用现有小读取器检查文件身份、状态、真实进程/返回、时间和依赖是否满足；报出具体缺口及下一动作。是否发现最近论文、匹配是否有鉴别力、机制是否新颖，需要链接实际材料和判断，不能由固定模板自动写成“已完成”或“正在进行”。
4. **反馈循环要有出口。** 对工程故障按“一个具体问题 → 最小修正 → 必要检查”处理，随后回到科学问题。已通过的组件仅因相关变化才重验；一次独立审查处理具体异议，不追求无休止的全员满意。科学负结果、缺匹配和 UNKNOWN 都是有效终点，不许修改条件或反复运行直到得到好结果。
5. **把释放的时间用于可否证的问题。** 工具维护的完成标准是下一步真实实验或近邻反证能更快开始，而不是增加脚本、票据或审查数量。每个有界维护任务收尾后恢复既定创新检索/实验；本次文章阅读期间已暂停论文检索，不宣称两者同时活跃。数据隔离、固定条件、失败保留和实际执行核验继续遵守原协议。

**建议的近期最小动作：** 下一次修改检查器时，将“当前阶段选择和证据入口”抽成一处数据驱动定义，保留已有历史记录；只核当前行为与一项旧记录读取兼容，不重跑旧科学实验。本审阅只给建议，未修改检查器、协议、账本、当前入口或运行程序，也未自动采用文章中的重试/合并策略。
