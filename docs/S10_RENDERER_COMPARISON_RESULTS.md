# S10：输出完全相同，本机选图组件约快7.78倍

这轮回答一个具体问题：能否保持原来的选图规则和结果，把最费时的逐像素计算改为批量计算？在本机两处已见场景、24个保存相机查询中，答案是可以。正式测量平均从 **1335.811毫秒降到171.767毫秒**，预定总时间之比 **7.776863**，耗时减少 **87.141%**。这是普通向量化工程优化；不由此宣称新算法创新、外部泛化或完整VMem视频加速。

## 结果保持到了什么程度

48次初始正确性、48次预热、240次正式测量，共336次选图调用全部通过。每次返回的面片编号、深度、视角余弦三数组，与原封存参考的形状、类型及C顺序字节完全相同，含正零/负零；完整票权、候选配额、姿态距离排序、NMS及有序最终4张照片也逐值相同。这里的三数组是几何缓冲，不能叫三张新拍照片。

执行前另有独立设计的60个人工边界案例，全部三数组逐字节相同；5个故意改错的实现均被测试拒绝。人工案例不是真实照片实验，也不构成任意输入的形式证明。

执行后不同作者重新打开全部336份实际NPZ、336份trace，比较1008个数组与24份原参考，完整trace比对106050个叶值；12,738项检查通过，包括冻结SHA、672文件清单、两个内嵌ZIP及统计复算。该检查读取真实保存输出，不只相信运行时PASS旗标；没有重跑渲染器或视频模型。依据：`S10_RENDERER_COMPARISON_INDEPENDENT_AUDIT.md`与`results/S10_renderer_comparison_independent_review/verification.json`。

另由比较工具作者编写不同脚本复算，224,547项检查通过；重新从24份缓冲累票并按已保存距离回放NMS，全部汇总字段及summary文件SHA相同。这是同作者不同脚本验证，不冒称不同作者。首次审计器把类内docstring缩进与去缩进方法直接比较，误拒后保留失败目录；只修审计器的源码规范化，原实验、门槛和结果未改，计时没有重跑。依据：`S10_RENDERER_RESULT_AUDIT.md`。

## 为什么这次比较成立

候选只替换原renderer中覆盖多边形的内层逐像素循环；投影、面片顺序、16边形、整数像素坐标、1e-15分母项、严格遮挡比较、FP32缓冲和空像素规则保留。候选把同一面片的像素计算交给NumPy批量处理，不缓存之前查询答案，不用原参考代替实际计算。恢复原循环后，完整方法AST与原版一致。

特别保留原Python float与float32缓冲的比较身份。固定NumPy2.3.5下改成显式float64会改变某些遮挡胜负，人工负对照已能检测这个错误。[NumPy NEP 50](https://numpy.org/neps/nep-0050-scalar-promotion.html)和[2.3标量规则](https://numpy.org/doc/2.3/reference/arrays.promotion.html#detailed-behavior-of-python-scalars)提供原始规则；本机探针见`S10_NUMPY_PROMOTION_REVIEW.md`。未验证跨版本等价。

双方同一进程、各六独立kernel、同一observer、小型占位上下文，原完整get_context_info没有S9计时插桩。外层时钟包含相机准备、渲染、投票、排序与NMS和上下文包装；文件读写、验证与证据保存均在计时之外，每对两次调用之间不插入保存/核验。两方只更换renderer绑定。

固定CPU、Python3.12.14 / NumPy2.3.5 / Torch2.7.0 / SciPy1.16.2，Torch intra/inter均8线程、默认FP32排序、FP64几何。五正式轮共AB/BA各60对，每查询只有3/2或2/3；其他本机进程未全面控制，顺序分组相近也不能消除全部噪声。峰值296910848字节是全进程峰值，没有单独比较两版内存。
